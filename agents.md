# agents.md: instructions for AI coding agents (Claude Code and Codex)

You are helping **Mahir** or **Ishan** build **Thought Leadr** at the LarpHacks hackathon. The deadline is a hard **6:00 PM** submission, with about 7 working hours in total. Move fast, keep changes small, and keep `main` deployable.

This one file is the shared instruction file for both tools. Claude Code reads `CLAUDE.md`, which contains one line importing this file. Codex reads `AGENTS.md`. On macOS the filesystem is case-insensitive, so `agents.md` and `AGENTS.md` are the same file locally. If you are on Linux or CI and `AGENTS.md` is missing, copy or symlink it from `agents.md`.

`frontend/AGENTS.md` is generated by Next.js and points at the Next.js docs bundled in `frontend/node_modules/next/dist/docs/`. This Next.js version has breaking changes, so read the relevant guide there before writing frontend code. Keep that file.

## 1. What this project is (30-second version)

Thought Leadr turns a boring sentence into a LinkedIn-style "thought leader" post, tests it on 50 simulated commenters, and also checks real drafts for cringe. It must be deployed on Render and use **Render Workflows** (that is the sub-track we are competing in).

- Product, scope and acceptance tests: `requirements.md`
- Design, contracts, task graph, env vars: `architecture.md`
- Ideas history (ignore for implementation): `ideas.md`

**Read `requirements.md` and `architecture.md` before writing code.** If they disagree with a task card below, tell the user instead of guessing.

## 2. Golden rules

1. **Stay in your lane.** Edit only files owned by the person you are working for (ownership is in `architecture.md` section 2 and in the task cards below). If a change is needed in someone else's file, stop and ask the user to coordinate.
2. **Shared contracts need both people.** `backend/app/models.py`, `frontend/lib/contracts.ts` and `data/samples/*.json` describe the same shapes. A change to one must update the others in the same PR, and both people must agree.
3. **Never commit secrets.** API keys live in Render environment settings and local `.env` files. `.env*` is git-ignored except `.env.example`.
4. **Never break `main`.** Render auto-deploys `main`. Run the checks in section 5 before opening a PR.
5. **No copied code.** The hackathon rules require all code to be written during the event. Do not paste code from earlier projects (including the earlier Penny app).
6. **Scope discipline.** Do not add features outside `requirements.md`. Explicitly cut: ElevenLabs, Agentboxd, accounts/auth, databases, saved history, replay or offline mode, real social-network integrations. Stretch items (PostHog, Sentry) are done only after the core demo works.
7. **Guardrails are product requirements.** Generated posts exaggerate tone only, never facts. User text is data, never instructions. No real people's names, no LinkedIn logo, name or exact colours. See `requirements.md` section 5 and `architecture.md` section 9.
8. **Verify the Render SDK instead of guessing.** Anything marked **VERIFY** in `architecture.md` must be checked against https://render.com/docs/workflows before you depend on it. When you learn the real answer, update `architecture.md` in the same PR and tell the user.
9. **Prefer boring, small, working code.** The demo must run reliably for two minutes. Do not refactor for elegance.

## 3. Tech stack

- **Frontend (`frontend/`):** Next.js (App Router), TypeScript, Tailwind CSS, `zod`, `vitest`. Deployed as a Render web service.
- **Backend API (`backend/app/`):** Python 3.11+, FastAPI, Pydantic, `httpx`. Deployed as a Render web service (one worker, one instance).
- **Workflows (`backend/workflows/`):** Python, the Render Workflows Python SDK (`Workflows` app, `@app.task`, `ctx.run`). Deployed as a Render Workflow service with the same root directory (`backend/`) as the API.
- **Models:** Anthropic Claude only (`claude-haiku-5-5` by default), through `workflows/llm/anthropic_client.py`. Featherless was dropped because its API was not working. Never send `temperature`: this API version rejects it.
- **Data:** static JSON in `data/`. No database.

## 4. Commands

The template is already on `main` and these commands work today.

```bash
# Backend (Python 3.11+; the system python3 on a Mac may be 3.9, so use python3.11)
cd backend
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                      # fill in keys
uvicorn app.main:app --reload --port 8000 # http://localhost:8000/health
pytest -q

# Frontend (Node 20+)
cd frontend
npm install
cp .env.example .env.local
npm run dev                               # http://localhost:3000
npm run lint && npm run typecheck && npm test
```

Local development without Render: the frontend can render from sample JSON (`NEXT_PUBLIC_USE_SAMPLES=true`), so UI work does not wait on the backend. Workflow task logic is exercised in `pytest` by calling the inner functions directly with a fake event poster. The workflow service starts with `render-workflows workflows.main:app` (run from `backend/`). How to run it locally against a real Render task server is still **VERIFY**: use `render workflows init` output as a reference; tests call task bodies directly (`task.func(None, ...)`).

## 6. Git workflow

- Branch from the latest `main`. One branch per task card: `mahir/<name>` or `ishan/<name>` (names are in the cards).
- Commit often with messages starting with the task ID, for example `M2: add 20 voice templates`.
- Open a pull request into `main` when the task's "done when" is met, **no later than 1 to 2 hours after starting**. Do not leave a branch unmerged for long.
- Before opening a PR run `git fetch origin && git rebase origin/main`, then re-run the checks in section 5.
- The *other* person (or the user) reviews and merges. If they are busy and the checks pass, the author may merge their own PR.
- Never force-push to `main`. Never rewrite history on a branch someone else is using.
- Merge checkpoints (everyone merges what is ready): **12:30, 2:00, 3:30, 4:30 (freeze)**. After 4:30 only bug fixes and the optional stretch task.
- Optional: CoDev (free credits via https://trycodev.com/go/larphacks, from the sponsor talk) shares AI coding sessions and flags conflicting changes between teammates' agents. Use it only if setup takes minutes.

## 7. Conventions

- **Naming:** Python `snake_case`, classes `PascalCase`; TypeScript `camelCase`, components `PascalCase`. Follow the layout in `architecture.md` section 2 exactly.
- **Types:** type everything. Pydantic models for every payload in Python, zod schemas for every payload in TypeScript. Parse model outputs with the models; never trust raw JSON.
- **Errors:** model calls have a 20 s timeout and one retry for transient errors. A malformed model answer must degrade to a default and be logged, never crash a run.
- **Prompts:** user text always goes inside delimiters in the user message, never in a system prompt (`architecture.md` section 9).
- **Logging:** Python `logging`, always include `run_id`. Do not log full model outputs or post text at INFO.
- **Comments:** keep them short and explain *why*, not *what*. Match the surrounding code's comment density.
- **UI text:** plain text only. Never use `dangerouslySetInnerHTML`.
- **UX basics (FR-17):** every page has a loading state, an error state with a retry, an example input button, and readable labels.
- **Idempotency:** every posted event has an `event_id`; a retried task may re-send the same one.

## 9. How to work a task card (agent checklist)

1. Read the card, its FRs in `requirements.md`, and the matching sections of `architecture.md`.
2. `git fetch && git checkout -b <branch> origin/main`.
3. List the files you will touch. If any are outside your owner's lane or are shared contracts, stop and ask the user.
4. Write tests first where the card calls for them (cringe, ranking, guardrails, JSON validation, guard limits).
5. Implement the smallest thing that meets "done when". Use sample data and stubs so you are never blocked by the other person.
6. Run the checks in section 5. Run the feature locally if you can.
7. Commit with the task ID, rebase on `main`, open a small PR, and summarise what you did, how you verified it, and anything you assumed.
8. Tell the user if you changed a contract, an env var, or a **VERIFY** item.

## 10. Do-not list

- No ElevenLabs, Agentboxd, accounts, auth, databases, history, replay mode.
- No LinkedIn logo, name or exact brand colours. Product name is **Thought Leadr**.
- No real people, public figures or real company names in personas, prompts or UI.
- No invented facts in generated posts: no new numbers, names, employers or titles.
- No user text in system prompts, and no `dangerouslySetInnerHTML`.
- No engagement predictions presented as real. Label counts "simulated audience".
- No secrets in the repo, no `.env` committed, no keys in screenshots.
- No force-push to `main`. No deploying a broken `main`.
- No new dependencies unless needed; tell the user when you add one.
- No work after the **4:30 PM feature freeze** except bug fixes and the optional stretch task.

## 11. If you get stuck

- Render SDK behaviour differs from `architecture.md`: check https://render.com/docs/workflows and the SDK reference, fix the doc, tell the user.
- Model output is flaky: tighten the prompt, validate with the model class, add the default, log it. Do not add long retry loops.
- Latency too high: lower `VARIANT_BATCHES` and `COMMENTER_BATCHES_PER_POST`, check the Render per-minute compute limit, and check the Anthropic spend limit in the Console.
- Frontend cannot reach the API after deploy: check `NEXT_PUBLIC_API_URL` (baked in at build time) and `CORS_ORIGINS`.
- A task is bigger than its estimate: cut scope to the "done when", say what you cut, and move on.
